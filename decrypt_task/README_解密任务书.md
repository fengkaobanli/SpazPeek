## 一、任务背景（一句话版）

AirPods Pro 2 通过 AACP 私有协议（L2CAP PSM 0x1001）向手机发送头部追踪数据。
**40ms 周期模式下，我们已经成功解码出姿态数据（与索尼 XM5 黄金真值 r>0.99）**；
**切到 20ms 高速模式后，帧率提升到 ~47fps，但头部方向数据"乱了"** ——需要解密 20ms 模式下的数据布局。

---

## 二、需要解决的问题（明确）

1. **解密 64 字节数据块的完整字段布局**（重点是：俯仰/偏航/滚转 三轴姿态字段的字节偏移、数据类型 int16/float、大小端、量纲）
2. **对比 40ms 模式 vs 20ms 模式的字段差异**（推测 20ms 模式字段位置或含义有变化，导致"方向乱"）
3. 确认帧内"计数/时间戳"字段含义（已知部分规律，见下）

## 三、已破译的协议结构（这是来之不易的成果，可直接引用）

### 3.1 帧总长度公式（已 100% 验证）

```
总长 = 13B 包头 + N × 64B 数据块 + 4B 包尾

实测样本：
  81B  = 13 + 64×1 + 4    （单帧）
 145B  = 13 + 64×2 + 4    （2 帧打包）
 209B  = 13 + 64×3 + 4
 273B  = 13 + 64×4 + 4
 337B  = 13 + 64×5 + 4
 401B  = 13 + 64×6 + 4
 465B  = 13 + 64×7 + 4
 529B  = 13 + 64×8 + 4
 593B  = 13 + 64×9 + 4    （9 帧打包，最大）
```

即：耳机会把多个 64B 头追数据块打包成一条 L2CAP 包发送。

### 3.2 13B 包头结构（已破译）

以 81B 帧为例：
```
04000400 17000000 1000 4500 08
│        │        │    │    └─ 固定 0x08
│        │        │    └─ 长度字段 LE16 = 总长 - 12
│        │        │       （81→0x0045, 145→0x0085, 209→0x00C5, 593→0x0245）
│        │        └─ 0x0010（含义未知，疑似版本/类型）
│        └─ opcode = 0x17（23，头追数据包）
└─ 固定魔数（AACP 协议标识）
```

### 3.3 64B 数据块结构（部分已知）

**块 0（每包第一个块）开头 4B 特殊**：形如 `xx xx 10 03`（如 `96111003`、`e2101003`）
**块 1~8 开头 4B**：uint16 LE 递增计数器（每次 +4），如 `6d4d0000` → `714d0000` → `754d0000` ...（+4 步进）
**包尾 4B**：计数器序列的延续（最后块 +4），如 `8d4d0000`

**所有块都含固定模式**：offset 4-11 为 `3a3e0810 1a3a01`（疑似"传感器数据头"标识）

### 3.4 已知的姿态字段（40ms 模式成功解码时的偏移）

40ms 模式下，以下解码已与索尼 XM5 交叉验证成功（相关系数 r>0.99）：
```
o1 = int16 LE @ b[43]    （从包起始字节算，含包头）
o2 = int16 LE @ b[45]
o3 = int16 LE @ b[47]

pitch = (o2n + o3n) / 2 / 32000 × 180   （度）
yaw   = (o2n - o3n) / 2 / 32000 × 180   （度）
其中 o2n/o3n = (原始值 − 校准时均值)
```

> 对应到"块 0 内部偏移"= 43−13=30、45−13=32、47−13=34。

### 3.5 历史注释线索（来自我们代码中的记录）

- 历史上出现过 **79B 帧**（非 81B），当时注释称之为"20ms 高速新格式，IMU 混合分量"，
  且当时的解码偏移是：o1@24、o2@45、o3@42 —— 但该版本未最终验证。
- **当前 20ms 高速模式下抓到的却是 81B 帧**（未见到 79B），说明这次的"高速"与历史上那次不同。

## 四、核心问题现象

| 模式 | 帧率 | 解码表现 |
|------|------|---------|
| 40ms（正常） | 25Hz | ✅ 姿态正确，与 XM5 r>0.99 |
| 20ms 高速（现状） | ~47fps | ❌ 用户实测"头部方向乱" |

**"乱"的量化表现**（用我们的解码器输出观测）：
- 静止时：字段看似正常（o2≈-25000 附近，缓慢漂移）
- **动作时（转头等）：值域爆炸** —— o2n（归一化值）从正常 ±500 飙到 **±47000**；
  原始 o2 从 -26000 跳变到 +23000（跨度≈48900，接近 int16 全量程的 3/4 圈）

## 六、求助目标（拿到此包的你应该做什么）

1. **定位 20ms 高速模式下真正的三轴姿态字段**（字节偏移 + 类型 + 量纲 + 符号）
   - 数据中有 XM5 黄金真值（xm5_sync.log）可作对照（时间戳对齐到毫秒）
   - 动作时间段已知（见时间线），可以做"单轴动作纯净窗口"相关性分析
2. 解释为什么 **40ms 模式能用的偏移（b43/45/47）在 20ms 模式下"乱"**
3. （可选）给出完整的 64B 块字段表

**注意事项（踩坑提醒）**：
- raw 日志中 `len=18`、`len=10` 等小包是 AACP 握手/控制包，非头追帧，可忽略
- 帧率参考：47fps ≈ 每 21ms 一条 81B 帧；25Hz 参照的 XM5 时间戳同样带毫秒
- **警惕伪相关**：三个动作窗口内 XM5 三轴自身可能存在耦合（用户转头时其他轴也动），
  建议使用偏相关/多元回归甄别，而不是简单两两相关
- 我们的初步扫描显示"动作窗口里 b43/b47↔左右轴 r≈0.99"等结果，
  但存在"同一字段跨轴高相关"的矛盾，需要更严谨的数学方法（见 ai_preliminary_analysis.md）
